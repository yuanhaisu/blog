在最近这个项目里，有一个瞬间让我意识到，自己对「一个人能交付多少软件」的判断已经过时了。

那天晚上，我在微信开发者工具里点下预览：老师端、家长端、管理后台同时亮起来，接口、权限、通知、接送记录都按预期工作。就在几个小时前，这些切片还只是计划文件里的几行任务。它们由一个主会话拆解，被不同的 agent 实现，再由一个全新上下文的 agent 逐项评审、在真机上验证，最后回到我这里做取舍。

那一刻我没有觉得「AI 替我写完了代码」。我想到的是另一件事：**一个人也可以设计一条交付流水线，让 agent 在里面干活，而人只负责判断、边界和证据。**

这就是「一人交付笔记」的起点。

![一人 + agent 的交付流水线](/images/one-person-delivery-pipeline.svg)

## 十一年，三个转折

过去十一年，我主要做后端与分布式系统。那段时间里，我关心的东西很具体：接口契约、数据一致性、并发、可观测性、故障恢复。后来有四年半时间，我带着一个小团队做数据分析，工作从「把代码写对」变成了「对交付结果负责」：需求是否值得做、模型是否真的有用、上线之后谁来维护。

再往后，我把重心放到 AI 模型服务与 LLM 应用上：把 YOLOv5、PaddleOCR 这类模型导出成 ONNX，部署到 Triton Inference Server；用 LLM 做意图识别和工具编排；在客户环境里做私有化部署，让数据不出门。

这三个阶段看起来跨度很大，但有一条线一直没变：**我关心的不是某个技术名词，而是一个东西能不能被稳定地交付出去。**

## 真正的转折点：把 agent 放进流水线

很多人对 AI 编程的想象是「补全更快」：写一行，AI 接下半行；写一个函数，AI 补一个测试。那当然有用，但它改变的是手感，不是交付方式。

真正改变交付方式的，是把 agent 放进一条完整的流水线里：

- 主会话只做编排，不读源码，只读计划和评审结论；
- 每个切片交给一个 worker 实现，切片足够小，失败可以回滚；
- 再由一个**全新上下文**的 supervisor 做对抗式评审，并在真实环境里验证；
- 检查点、validator、密钥扫描和进度文件把过程留下来，而不是只留下「我觉得写完了」。

这套流程并不神秘，也不轻松。它要求你把「怎么做」拆成「怎么验收」，要求你接受 agent 会在某些任务上反复失败，也要求你承认：**人最有价值的部分，不是敲代码的速度，而是定义边界和判断取舍。**

## 一人交付，不是「AI 取代团队」

我不想把这件事写成「一个人干掉一个团队」的故事。真实情况更朴素：

- agent 可以承担大量实现、测试补齐、重复修改和文档整理；
- 但需求是否成立、架构是否过度、风险是否可接受，仍然要人判断；
- 评审必须独立，最好由没有参与实现的上下文来做；
- 交付的证据要能复核：测试、日志、检查点、回滚路径。

所以「一人交付」不是把人去掉，而是把人的位置往前移：从执行者变成流水线的设计者。一个人能不能交付一套企业级软件，取决于这条流水线设计得好不好，而不是模型参数有多大。

## 这个博客写什么

我会把「一人交付实验」拆成可复核的记录，而不是只展示结果：

- 一人公司的软件交付方法：范围控制、架构取舍、质量门槛；
- AI agent 流水线的实际用法：任务编排、上下文管理、验证与回滚；
- 真实项目的复盘：指标、失败、成本与时间线；
- 可复用清单：哪些做法能直接被读者拿走。

这个专题的第一篇正式复盘，是我用约 2.5 个月、一个人加一条多 agent 流水线交付的一套多租户 SaaS。它不是一个玩具项目：后端约 300 个接口、70 张表，前端约 130 个组件，包含老师端、家长端两个微信小程序和一个管理后台。下一篇会完整拆开它的架构、流水线和失败路径。

第三篇会回到 AI 工程本身：模型服务、LLM 工具编排、数据与算法三层怎么一起落地。如果你在做 AI 应用，或者正在判断「私有化部署到底该从哪里开始」，那一篇会更接近你的日常。

## 这个博客不写什么

- 不写无法验证的成功学；
- 不写「AI 全自动交付」的神话；
- 不暴露客户名称、儿童信息、手机号、内部域名或任何密钥；
- 不把 AI 生成的内容当作未经审查的事实。

每一篇都尽量给出可复核的过程与证据。你可以不同意我的结论，但应该能看清我是怎么走到那里的。
