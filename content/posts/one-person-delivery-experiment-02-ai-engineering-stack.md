很多 AI 项目的失败，不是模型选错了，而是只做了「模型」这一层。

一个能交付的 AI 应用，通常要同时解决三件事：模型怎么稳定地跑起来、LLM 怎么和业务工具接上、数据与算法怎么形成闭环。我把它们叫做 AI 工程落地的三层栈。这篇用我做过的金融级私有化项目拆开讲。

![AI 工程落地的三层栈](/images/ai-engineering-stack.svg)

## 第一层：模型服务，不是「写个 Flask 调模型」

模型服务层要回答的问题很具体：模型怎么加载、怎么批处理、怎么在 CPU/GPU 之间切换、怎么预热、怎么观测、怎么升级。

在内容识别场景里，我用 YOLOv5 做检测、PaddleOCR 做文字识别（det + rec），模型导出 ONNX 后部署到 Triton Inference Server。Triton 里维护了 5 个模型仓库：检测和识别走 ONNX Runtime backend，前后处理用 Python backend 自己实现；`max_batch_size` 最高到 1000，其中 2 个模型配置了 model warmup。

对外接口是 Flask + waitress，部署在 Kubernetes 的 Deployment / Service 上。客户环境不一定有 GPU，所以同一套服务提供 CPU / GPU 双版本；在没有 GPU 的银行客户环境里，CPU 版本稳定吞吐大约 7–10 req/s，具体会随请求内容大小浮动。

![Triton 模型仓库与 CPU/GPU 双版本](/images/triton-model-repos.svg)

这一层最容易被低估的是「前后处理」。检测框怎么裁、OCR 的 det/rec 怎么串、图片怎么归一化、批量请求怎么拼，这些都不在模型文件里，却直接决定吞吐和准确率。把它们放进 Python backend，而不是散落在业务代码里，是我认为最值得的一个取舍。

## 第二层：LLM 应用，重点是工具编排

LLM 应用层不是「接一个聊天接口」就结束了。真正的价值在于：把自然语言变成对内部系统的可靠调用。

我做过两个方向：

**AI 智询**：用户用自然语言描述需求，系统做意图识别，然后路由到最合适的内部接口或工具，完成多步调用。它把过去需要在菜单里点很多次的流程，收敛成一次对话。难点不在 prompt，而在工具边界的定义：哪些工具可以暴露、参数怎么校验、失败怎么回滚、权限怎么继承。

**AI 鉴敏**：用语义分析识别用户行为与内容中的敏感信息，相比关键词匹配降低误判。它同样私有化部署在客户环境里，数据不出门。

这两个应用有一个共同约束：**私有化部署**。模型、向量、日志、工具调用都不能离开客户环境。这个约束会反过来影响架构：你不能依赖一个云端 LLM API 做所有事，要在本地做模型服务、缓存、降级和审计；你也不能把业务数据随便塞进第三方工具。

## 第三层：数据与算法，决定系统是不是「越用越准」

第三层最容易被忽略，但它决定 AI 应用是不是只有 demo 价值。

在用户行为分析场景里，系统每天采集千万级的桌面操作元事件。我们用 Python + Pandas / NumPy 按业务配置的异常规则做清洗、转换与特征工程，归纳到约 30 万条样本、4–10 维特征（分类 + 数值），在模型效率与检出效果之间取平衡；日均百万级预测。

另一块是事件序列关联分析。我独立设计并实现了一个轻量的事件序列正则引擎：

- 词法 / 语法分析 → AST → 后缀 IR → Thompson ε-NFA 构造与匹配；
- 支持并、连接、分组、有界重复 `{n}` 与无序组 `<...>`；
- 带 `mustMatchPos` 位置约束的反向匹配，保证刚到达的事件必须参与；
- 用字符集、长度 100、编译规模 3000、无序单元 5 四层约束规避灾难性回溯；
- 核心 pass 都有单元测试。

![事件序列正则引擎](/images/event-sequence-regex.svg)

这段经历给我的最大提醒是：**AI 工程不是只有模型。** 数据怎么采、特征怎么造、规则怎么表达、失败怎么解释，往往比换一个更大的模型更能决定系统能不能上线。

## 工程取舍：为什么没有做 RAG 和微调

这套系统没有做 RAG，也没有做微调。不是这些技术不好，而是场景不匹配：

- 客户环境要求私有化，数据不能出门；
- 业务问题更多是「识别 + 路由 + 规则」，不是开放域问答；
- 微调需要稳定的标注数据和持续评估，项目周期内不成立；
- 先把模型服务、工具编排、数据闭环做稳，收益比追新更大。

同理，Triton 也不是唯一选择。如果只是低频调用，一个 Flask 服务就够了；但当你要批处理、要多模型仓库、要在 CPU/GPU 之间切换、要做 warmup 和观测，Triton 的价值才会显现。技术选型应该由交付约束驱动，而不是由技术名词驱动。

## 可复用清单

1. 先把模型服务做成独立层，不要让业务代码直接加载模型。
2. 前后处理也属于模型服务，不要散落在业务里。
3. 私有化场景先设计降级路径：没有 GPU、没有外网、模型升级失败时怎么办。
4. LLM 应用先定义工具边界和权限，再谈 prompt。
5. 数据与算法层要能解释「为什么命中」，否则无法在客户环境里维护。
6. 不要为了追新引入 RAG/微调；先确认场景真的需要。
7. 吞吐数字要写清测试条件，不要把实验室数字当成生产承诺。

## 回到「一人交付」

这三层栈看起来是技术问题，其实也是交付问题：一个人要同时扮演模型工程师、后端工程师、数据工程师和运维，唯一的办法是把边界切清楚，让每一层都能独立验证。
