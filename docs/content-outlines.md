# 首发内容提纲（3 篇博客 + 2 篇平台稿）

> 目标：把 `content/` 从 0 篇变成 3 篇中文博客 + 2 篇平台稿，满足 v1 上线门槛。
> 状态（2026-11-05）：提纲已确认；3 篇博客初稿已写入 `content/posts/`；2 篇平台稿待写。
> 使用方式：先确认本提纲，再写全文；每篇博客写入 `content/posts/`，平台稿在知乎/公众号发布。

## 0. 通用规则

### 0.1 博客 frontmatter

```yaml
---
title: <标题>
description: <一句话摘要，80–120 字>
date: 2026-11-<DD>
tags: [一人交付, ...]
series: one-person-delivery-experiment
order: <1|2|3>
draft: false
featured: <true|false>
launch: true
lang: zh
license: CC BY 4.0
---
```

- 三篇博客属于同一专题：先在 `content/series/one-person-delivery-experiment.md` 写真实专题元数据（`title: 一人交付实验` + 描述），不要沿用测试专题。
- `launch: true` 会触发内容护栏：至少 3 个不同站内链接 + 至少 1 张站内原创图。
- 每篇至少 1 张原创图；图片放 `public/images/`，优先 SVG/WebP/AVIF，Markdown 用站内绝对路径引用。
- 不写客户名称、幼儿园名称、儿童信息、手机号、内部域名、密钥；案例统一写「某民办幼儿园」「金融行业客户」。
- 所有数字以你最终确认的版本为准；简历中「300+ 接口 / 70+ 表」与「298 接口 / 70 表」两个版本，正文建议写「约 300 个接口、70 张表」。

## 1. 《我为什么开始「一人交付笔记」》

- **目标读者**：独立开发者、一人公司、想用 AI 提升交付效率的工程师
- **核心论点**：一个人 + AI agent 的交付边界，取决于人设计的流水线，而不是模型本身
- **目标关键词**：一人公司、AI 交付、独立开发、AI Agent、个人品牌
- **长度**：3000–4500 中文字
- **Frontmatter**：`order: 1`、`featured: true`、`launch: true`
- **配图**：`/images/one-person-delivery-pipeline.webp`（一人 + agent 交付流水线总览）

### 结构

1. **开场：一个具体的交付瞬间**
   - 不写履历堆砌；从一个真实场景切入：某天发现一个人可以在一天内完成过去需要多人协作的「实现 → 测试 → 评审 → 部署」闭环。
2. **过去 11 年的三个转折**
   - 后端与分布式系统：工程规范、稳定性、可观测性。
   - 数据分析部门主管：从写代码到对交付结果负责。
   - AI 模型服务与 LLM 应用：Triton、YOLO/OCR、意图识别与工具编排。
3. **真正的转折点：把 agent 放进研发流程**
   - 不是「让 AI 写代码」，而是把需求拆解、实现、评审、验证、回滚设计成流水线。
   - 一人交付的关键：哪些环节必须由人判断，哪些可以自动执行，失败如何留下证据。
4. **为什么叫「一人交付实验」**
   - 不是「AI 取代团队」，而是「人 + 流水线 + 证据」。
   - 公开记录过程、失败与取舍，而不是只展示结果。
5. **这个博客写什么 / 不写什么**
   - 写：一人公司的交付方法、agent 流水线、真实项目复盘、可复用清单。
   - 不写：成功学、无法验证的结论、客户/儿童/密钥信息。
6. **接下来三篇的路线图**
   - 链接到第 2 篇、第 3 篇、About。
7. **结尾 CTA**
   - RSS / 公众号订阅；知乎/公众号讨论入口。

### 写作要点

- 第一人称，具体、克制；避免「AI 将取代团队」这类标题党。
- 至少 3 个站内链接：第 2 篇、第 3 篇、About。
- 结尾给读者一个可执行的下一步：先设计一条最小 agent 流水线，再谈规模。

## 2. 《一人交付实验 #1：一个人 + 多 agent，2.5 个月交付 14 万行 SaaS》

- **目标读者**：独立开发者、技术负责人、想验证「一人公司」可行性的人
- **核心论点**：一人交付的可行性来自流水线与工程规范，不是熬夜或模型魔法
- **目标关键词**：一人开发、多 agent、多租户 SaaS、Go、AI Agent、独立开发
- **长度**：5000–7000 中文字
- **Frontmatter**：`order: 2`、`featured: true`、`launch: true`
- **配图**：
  - `/images/nurture-planet-architecture.webp`（三端 + 后端架构）
  - `/images/multi-agent-pipeline.webp`（orchestrator → worker → supervisor）
  - `/images/multi-tenant-isolation.webp`（`kindergarten_id` 隔离）

### 结构

1. **问题与约束**
   - 某民办幼儿园的家园共育痛点：通知触达、请假、接送、成长记录、纠纷留痕。
   - 为什么传统外包/团队方案不划算：预算、沟通成本、迭代速度。
2. **交付结果（先给结论）**
   - 约 2.5 个月；后端约 300 个 Go 文件 / 7 万行（含约 2.2 万行测试）；300+ 接口、70+ 表；前端约 130 个 Vue 组件 / 7 万行；合计约 14 万行。
   - 两个微信小程序（老师端、家长端）+ Nuxt 3 管理后台 + Go 后端。
   - 说明「AI 生成 + 人工评审」，不夸大「全自动」。
3. **架构**
   - Go 1.25 + Gin + GORM + MySQL + Redis + Casbin + JWT + Wire。
   - 分层：handler → service → repository → domain。
   - 多租户：所有业务表带 `kindergarten_id` 强制隔离；儿童照片仅授权家长可见。
   - 人脸识别：Provider 接口接腾讯云 IAI，1:N 检索；供应商退市时只换实现层。
4. **三端**
   - 老师端/家长端：uni-app + Vue 3 + Vite。
   - 管理后台：Nuxt 3 + Element Plus + Pinia + ECharts。
   - 设计 Token：三端共享 `tokens.json`，lint 阻断硬编码。
5. **多 agent 流水线（核心章节）**
   - 主会话只做编排，不读源码；只读计划与 verdict。
   - `slice-worker`：按切片实现。
   - `slice-supervisor`：全新实例、对抗式评审、微信开发者工具真机验证。
   - 四检查点 + validator + 密钥扫描；状态落 `PROGRESS.md`。
   - 为什么用「全新实例」评审：避免同一个上下文自我确认。
6. **工程规范**
   - API 契约优先：`backend/api/` 是接口形状唯一真相源。
   - OpenSpec：跨三层改动先写 SHALL + Scenario 验收标准。
   - 测试：Go testify + 前端 Vitest。
   - 迭代复盘：哪些规范真正降低了返工。
7. **失败与取舍**
   - agent 在哪些任务上失败最多（跨文件重构、UI 视觉、真机兼容）。
   - 评审开销与上下文管理；哪些环节必须人来做。
   - 如果重来一次，会改哪三件事。
8. **可复用清单**
   - 读者可以直接抄走的 5–7 条：切片大小、评审隔离、契约优先、检查点、证据留存。
9. **下一步**
   - 公开案例仓库 `nurture-planet-case-study`（脱敏）；第 3 篇拆 AI 工程栈。

### 写作要点

- 先给结果，再讲过程；每个结论尽量配数字或失败案例。
- 至少 3 个站内链接：第 1 篇、第 3 篇、专题页。
- 脱敏：不出现幼儿园名称、园长/家长/儿童姓名、真实截图、内部域名、客户合同信息。
- 不把「14 万行」写成纯 AI 产出；明确「AI 生成 + 人工评审 + 测试」。

## 3. 《一人交付实验 #2：AI 工程落地的三层栈》

- **目标读者**：后端工程师、AI 应用开发者、需要私有化部署的技术负责人
- **核心论点**：AI 落地不是选一个模型，而是模型服务、工具编排、数据/算法三层一起交付
- **目标关键词**：AI 工程、Triton、YOLOv5、PaddleOCR、LLM 工具编排、私有化部署、Go
- **长度**：4000–6000 中文字
- **Frontmatter**：`order: 3`、`featured: false`、`launch: true`
- **配图**：
  - `/images/ai-engineering-stack.webp`（三层栈总览）
  - `/images/triton-model-repos.webp`（Triton 模型仓库）
  - `/images/event-sequence-regex.webp`（事件序列正则引擎）

### 结构

1. **三层栈总览**
   - 模型服务层、LLM 应用层、数据/算法层；为什么三层必须一起设计。
2. **模型服务层：YOLOv5 + PaddleOCR + Triton**
   - 内容识别：网页/图片中的文字与元素。
   - 模型导出 ONNX → Triton；检测/识别走 ONNX Runtime backend，前后处理用 Python backend。
   - 5 个模型仓库；`max_batch_size` 最高 1000；2 个模型配置 warmup。
   - CPU/GPU 双版本；无 GPU 的银行客户环境用 CPU，稳定吞吐 7–10 req/s（随内容大小浮动）。
   - Flask + waitress 接口；K8s Deployment/Service。
3. **LLM 应用层：意图识别 + 工具编排**
   - AI 智询：自然语言解析意图 → 路由到内部接口/工具 → 完成调用；把多步菜单收敛为一次对话。
   - AI 鉴敏：语义敏感识别 vs 关键词匹配；降低误判。
   - 私有化部署：数据不出客户环境；为什么这决定了架构取舍。
4. **数据/算法层：行为分析与事件序列正则**
   - 千万级/日桌面操作元事件；Pandas/NumPy 清洗、转换、特征工程；约 30 万条样本（4–10 维）；日均百万级预测。
   - 事件序列正则引擎：词法/语法 → AST → 后缀 IR → Thompson ε-NFA；并、连接、分组、有界重复、无序组；`mustMatchPos` 反向匹配；四层约束规避灾难性回溯；核心 pass 单元测试。
5. **工程化取舍**
   - Triton vs 纯 Flask：批处理、并发、模型仓库管理。
   - CPU/GPU 双版本的成本与运维。
   - 可观测性、失败模式、模型更新与回滚。
   - 为什么没有做 RAG/微调：场景与约束不匹配。
6. **可复用清单**
   - 三层栈的最小落地顺序；哪些先做、哪些后做；常见坑。
7. **结尾**
   - 链接回第 1 篇、第 2 篇、About；欢迎讨论。

### 写作要点

- 以「交付约束」驱动技术选择，而不是罗列技术名词。
- 至少 3 个站内链接：第 1 篇、第 2 篇、About。
- 不写客户名称、内部接口、模型权重、真实数据；吞吐数字注明测试条件。
- 代码片段只保留决策相关的配置/接口形状，不贴大段实现。
