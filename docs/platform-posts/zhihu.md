# 一个人如何用 AI agent 交付一套多租户 SaaS？

先说结论：能，但前提不是「模型更强」，而是你把交付拆成可验收的切片，并让评审发生在没有沉没成本的全新上下文里。

我最近用约 2.5 个月，一个人加一条自建的多 agent 流水线，交付了一套面向民办幼儿园的家园共育 SaaS。后端 Go，约 300 个接口、70 张表；前端约 130 个 Vue 组件；两个微信小程序加一个管理后台；代码合计约 14 万行，由 AI 生成、人工评审和测试兜底。

这篇不复述「AI 多强」，只讲一件事：一个人怎么把交付组织起来。

## 先看结果

| 维度 | 结果 |
| --- | --- |
| 周期 | 约 2.5 个月 |
| 后端 | Go，约 7 万行（含约 2.2 万行测试），约 300 个接口、70 张表 |
| 前端 | 约 130 个 Vue 组件，约 7 万行 |
| 端 | 老师端小程序、家长端小程序、Nuxt 3 管理后台 |
| 合计 | 约 14 万行（AI 生成 + 人工评审） |

这不是「AI 全自动写完」。真正决定能不能交付的，是切片、契约、评审隔离和证据留存。

## 一个切片长什么样

「切片」听起来抽象，举个例子。

「通知已读状态」这个需求，我不会把它写成「把通知模块做出来」，而是拆成一个可验收的切片：数据库增加已读记录；接口返回当前用户的已读状态；老师端显示已读人数；家长端在打开通知后标记已读；管理员能看到未读名单；权限上，家长只能标记自己的记录。

worker 拿到的是契约、相关文件范围和验收条件，不是「你看着办」。supervisor 评审时也不需要理解整个系统，只需要确认：契约有没有被遵守、权限有没有越界、已读状态在并发下会不会重复、真机上打开通知后状态有没有变化。

切片足够小，失败可以回滚；切片足够完整，评审就能在真实行为上做判断。这两件事同时成立，agent 才不会变成「写得很快、返工更多」的工具。

## 不是让 AI 写代码，是让 agent 进流水线

很多人对 AI 编程的理解是「补全更快」。那改变的是手感，不是交付方式。

我把交付拆成四个角色：

1. **主会话只做编排**。它不读源码，只读计划、切片状态和评审结论。这样主上下文不会被几十万行代码淹没，决策和执行也分开了。
2. **slice-worker 负责实现**。每个切片足够小，有明确的输入、输出和验收标准；失败可以回滚。
3. **slice-supervisor 负责对抗式评审**。它是一个全新上下文的实例，不继承 worker 的自我判断；它读代码、跑测试、在微信开发者工具里做真机验证，再给出 verdict。
4. **检查点与证据**。四个检查点、validator、密钥扫描，状态全部落在 `PROGRESS.md`。没有证据，不算完成。

四个检查点分别看：规格是否写清楚、契约是否稳定、实现是否越层、真机行为是否符合验收。validator 负责机械检查：编译、测试、lint、密钥扫描、禁止的依赖。

为什么 supervisor 要用全新实例？因为同一个上下文里，模型很容易为自己的实现找理由。换一个没有沉没成本的实例，评审会更接近真正的外部 reviewer。这一点在跨文件重构和权限边界上尤其明显。

## 架构：只讲三个关键决定

后端是 Go + Gin + GORM + MySQL + Redis，权限用 Casbin，依赖注入用 Wire，分层是 handler → service → repository → domain。

**决定一：用 Go，而不是追新框架。** 一人项目需要部署简单、并发模型清楚、错误处理显式。一个二进制、一套标准库，比一堆框架魔法更适合长期维护。

**决定二：共享表 + 租户列，而不是每租户一个 schema。** 前者实现简单，但要求每一层都记得带租户条件。我把「忘记租户条件」当成最高级别缺陷：repository 强制注入，code review 看到跨园所查询直接拒绝，测试专门覆盖跨租户读取。儿童照片只对授权家长可见。

**决定三：人脸识别用 Provider 接口，而不是直接绑供应商。** 接腾讯云 IAI 做 1:N 检索；供应商方案调整时，只替换实现层，调用方零改动。对一人项目来说，这种「可替换边界」比「选对某个供应商」更重要。

三端分别是：老师端/家长端 uni-app + Vue 3，管理后台 Nuxt 3 + Element Plus + Pinia + ECharts；三端共享设计 Token，用 lint 阻断硬编码。

## 失败与代价

这套流水线不是没有成本。几个真实的失败点：

- **跨文件重构仍然最容易失控**。切片一旦跨过太多文件，worker 很容易改出「局部正确、整体不一致」的结果；后来我把这类任务拆成「先改契约，再改实现，再改调用方」。
- **UI 细节和真机兼容需要人盯着**。小程序的样式、键盘、滚动、真机表现，agent 可以写，但很难自己判断「看起来对不对」。
- **评审开销是真实成本**。全新上下文的 supervisor 会增加时间，但它减少的是更贵的返工；切片太大时，评审开销会迅速失控。
- **上下文管理比模型能力更关键**。主会话不读源码、切片足够小、状态落到文件，这些做法比换一个更强的模型更能提升稳定性。

如果重来一次，我会改三件事：切片再小一点；真机验证再早一点；契约测试再多一点。

## 什么情况下不要用这套方法

- 需求极不稳定，今天做 A、明天推翻 A；
- 界面极重，视觉判断占主导，agent 很难自己验收；
- 强实时协作，多人同时修改同一模块；
- 团队已经有成熟流程，缺的不是执行速度，而是方向。

一人交付不是万能方法。它只是把「一个人能做的事」往前推了一点，同时把「人必须判断的事」暴露得更清楚。

## 一个反例

我也试过把「重构整个通知模块」直接丢给一个 worker。结果它改得很勤快，单个文件看起来都合理，但调用方没有同步，权限边界也没有覆盖。最后我花的时间比手写还多。

这次失败让我确认了一件事：**切片不是「任务小」，而是「验收边界清楚」**。一个切片可以很小，但如果它的影响面跨过多个模块，它就不适合交给一个没有全局上下文的 worker。后来我把这类任务拆成「先改契约，再改实现，再改调用方」，每一步都能单独验收，返工才降下来。

## 如何开始

如果你也想试，先不要从「重构整个项目」开始。选一个边界清楚、能独立验收的小功能：

1. 写清楚输入、输出和验收标准；
2. 把相关契约和文件范围交给一个 worker；
3. 用另一个全新上下文做评审；
4. 在真实环境里验证，不靠「看起来对」；
5. 留下测试、日志和回滚路径。

跑通一个切片，再谈扩大。

最后提醒一句：不要用「代码行数」衡量这套方法。行数只能说明生成速度，不能说明可维护性。真正该看的是返工率、评审通过率和线上故障率；如果这三个指标没有变好，说明流水线还没有设计对。

## 可复用清单

1. 按可交付行为切片，不要按文件切片。
2. 每个切片先写验收标准，再让 agent 实现。
3. 评审必须用没有参与实现的上下文。
4. 主会话不要读全部源码，只读计划和 verdict。
5. 契约优先，测试放在契约和真实行为的交界处。
6. 每个阶段留下证据：测试、日志、检查点、回滚路径。
7. 对外复盘前先脱敏：客户名称、儿童信息、内部域名、密钥，一个都不能留。
