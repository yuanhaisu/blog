# 一人公司的 AI 交付实验：第一期复盘

2.5 个月，一个人，一套多租户 SaaS，约 14 万行代码。

这不是「AI 帮我写完了」的故事。真正让我意外的，不是模型能写多少代码，而是当我把交付拆成流水线之后，一个人可以同时扮演产品、后端、前端、测试和运维，而且每一步都能留下证据。

## 先看结果

这是一套面向民办幼儿园的家园共育与园务管理 SaaS：老师端、家长端两个微信小程序，加一个管理后台；后端 Go，约 300 个接口、70 张表；前端约 130 个 Vue 组件；代码合计约 14 万行，由 AI 生成、人工评审和测试兜底。

周期约 2.5 个月。

我知道这个数字很容易被误读，所以先把边界说清楚：它不是「AI 全自动写完」，也不是「一个人替代一个团队」。它是一个人设计了一条流水线，把实现、评审、验证和证据留存拆成了可重复的环节。

## 三个关键判断

### 1. 流水线比模型重要

很多人把 AI 编程理解成「补全更快」。那改变的是手感，不是交付方式。

我把交付拆成四个角色：主会话只做编排，不读源码；`slice-worker` 实现切片；`slice-supervisor` 用全新上下文做对抗式评审，并在微信开发者工具里真机验证；检查点、validator、密钥扫描把证据留在 `PROGRESS.md`。

为什么 supervisor 要用全新实例？因为同一个上下文里，模型很容易为自己的实现找理由。换一个没有沉没成本的实例，评审会更接近真正的外部 reviewer。

### 2. 契约和测试是 agent 的护栏

agent 不会自动遵守你脑子里的规范，除非规范被写成可执行的约束。

这个项目里最起作用的是四件事：API 契约优先（改接口先改契约）；OpenSpec 规格驱动（跨三层改动先写 SHALL + Scenario）；Go testify + 前端 Vitest；每个阶段留下可验证的产物。

规范听起来像「大团队才需要的东西」，但在一个人 + agent 的场景里反而更重要：agent 越快，没有约束的返工就越贵。

### 3. 人的位置往前移

一人交付不是「AI 取代团队」。真实情况是：

- agent 承担大量实现、测试补齐、重复修改和文档整理；
- 但需求是否成立、架构是否过度、风险是否可接受，仍然要人判断；
- 评审必须独立，最好由没有参与实现的上下文来做；
- 交付的证据要能复核：测试、日志、检查点、回滚路径。

人最有价值的部分，不是敲代码的速度，而是定义边界和判断取舍。

## 两个失败

**跨文件重构仍然最容易失控。** 切片一旦跨过太多文件，worker 很容易改出「局部正确、整体不一致」的结果。我遇到过一次权限相关的改动：单个文件看起来都对，但调用方没有同步，评审时才发现跨租户的路径没有被覆盖。后来我把这类任务拆成「先改契约，再改实现，再改调用方」，并且要求每个切片都带一个跨租户的测试。

**UI 细节和真机兼容需要人盯着。** 小程序的样式、键盘、滚动、真机表现，agent 可以写，但很难自己判断「看起来对不对」。supervisor 的真机验证是必要的，但仍然需要人做最终取舍。有一类问题只有在真机上才出现：键盘弹起后布局被顶起、滚动位置丢失、某些机型上字体渲染不一致。这些不是「代码写错了」，而是「没有在真实环境里看过」。

如果重来一次，我会改三件事：切片再小一点；真机验证再早一点；契约测试再多一点。

## 时间花在哪里

2.5 个月里，真正写代码的时间没有想象中多。大致可以分成四块：

- **产品与范围**：把「什么都想要」压到「这一版必须有什么」，这部分只能人做；
- **架构与契约**：定分层、租户模型、接口形状、设计 Token，这部分决定后面返工多少；
- **实现与评审**：agent 写、supervisor 审、我处理冲突和边界；
- **真机与收尾**：小程序兼容、权限边界、异常路径、部署与文档。

AI 明显加速的是第三块；第一、二、四块反而更需要人。这个分布也解释了为什么「一人 + agent」不是简单地把人替换掉：它把人的工作从「写」推向了「定义」和「判断」。
